# Feature status

Status of every feature in version 0.1.0, as of **2026-09-25**. It is derived
from the build reports of each vertical slice and re-checked against the
current code and tests after the audit fixes of 2026-09-24 and the second,
third, and fourth rounds of fixes on 2026-09-25 (every status below was
checked against the code after the fourth round landed; see "Audit fixes"
and the rounds of fixes under "Unreleased" in [CHANGELOG.md](../CHANGELOG.md)).
Spec section 32 requires exactly four statuses:

| Status | Meaning |
| --- | --- |
| `implemented-and-tested` | The code exists and offline automated tests exercise it. No live provider is needed for the behavior to be meaningful (for example budgets, routing, approvals, vault writes). |
| `implemented-awaiting-credentials` | The code exists and is tested offline against fakes or synthetic fixtures built from the provider's documented contract, but it has **never run against the live service**. A first real run needs your credentials (or, for the container and CI, Docker or a GitHub repository). |
| `optional-disabled` | Off by default by design. Turning it on needs explicit configuration, an approval, or an optional package. |
| `genuinely-incomplete` | Missing or only partly implemented. The gap is stated. |

**The single most important fact:** no integration was tested live. No
credentials were available or used, and no paid request was made. Everything
that talks to Google, the LLM Gateway, DataForSEO, Apify, PageSpeed/CrUX, a
running Qdrant, a real browser, or GitHub Actions is at best
`implemented-awaiting-credentials`. The first live run may surface response
details the fixtures do not model; `doctor --network` and each status command
report what could and could not be verified.
