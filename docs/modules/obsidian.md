# Obsidian-compatible vault (`src/obsidian`)

The vault is a folder of plain Markdown files, one per site, at
`<workspace>/vault/<site-id>/`. It is useful in any text editor. Obsidian
features (wikilinks, properties, callouts) are layered on top, and nothing
depends on community plugins.

## Ownership

| Where | Owner | Notes |
| --- | --- | --- |
| `01 Business/` | Human | Business facts and standing decisions. seo-agent never writes here (the writer refuses). It reads these notes only through the validated, versioned business sync. |
| Text outside the generated markers | Human | Preserved verbatim on every render. |
| Properties a human adds to a generated note, and the entries a human adds to `tags`, `aliases`, `cssclasses` | Human | Kept on every render with their values, YAML comments, key order, and quoting: the frontmatter is edited in place, only generated keys are set or removed. (If an in-place edit cannot be verified by parsing it back, the block is re-serialized from values instead: values are kept, comments inside the frontmatter are lost, and a warning is logged.) |
| Text between `<!-- seo-agent:generated:start -->` and `<!-- seo-agent:generated:end -->`, and the generated properties | seo-agent | A presentation of SQLite records, regenerated by `vault render`. |
| SQLite (`vault_notes`, `business_note_versions`, all measurement tables) | seo-agent | The source of truth. Editing a note never changes it. |
| Qdrant | seo-agent | A rebuildable search index, never authoritative (see the memory module). |

## Writer design

`writeGenerated(note)`:

1. Validate the vault-relative path. Absolute paths, `..`, empty segments, NUL,
   backslashes, hidden segments (for example `.obsidian`), and link-breaking
   characters are rejected. Generated notes may only go into the standard
   folders, never `01 Business/` or `Templates/` (human-owned) and never
   `14 System Logs/` (append-only; use `appendSystemLog`).
2. Resolve the path with `safeResolve` and additionally `lstat` every
   component: each parent must be a real directory and nothing inside the
   vault may be a symlink (even one that points inside the vault). Missing
   parents are created one component at a time and re-checked.
3. Build the generated properties in a stable order: `id`, `type`, `site`,
   `generated_at`, `source_ids`, `title`, then renderer properties, then
   `synthetic` (demo) and `tags`. Renderer properties cannot override the core
   keys, and nested objects are rejected (Obsidian does not support nested
   properties). Strings are made single-line so they round-trip through YAML.
   Every text value except `id`, `type`, `site`, and `generated_at` comes from
   the database (page and source titles, keywords, model output), so it is made
   inert for Obsidian's Properties view: `[[` and `]]` become `[ [` and `] ]`,
   `](` becomes `] (`, and a URI with a scheme other than http(s) (for example
   `obsidian://`) becomes `scheme: //`. Generated properties never contain
   links; links belong in the body.
4. Hash the generated part: generated properties except `generated_at` and the
   shared list keys (`tags`, `aliases`, `cssclasses`), plus the normalized
   region (LF line endings, no trailing whitespace). Empty values (`null`,
   `''`, `[]`) hash the same so harmless re-serialization by an editor does
   not look like an edit. The shared list keys are excluded because the owner
   may add entries to them (see step 8).
5. New file: create-only atomic write (temp file, fsync, hard link to the final
   name, which fails instead of overwriting; directory fsync).
6. Existing file: parse strictly. The writer creates a conflict artifact and
   does not touch the note when:
   - the note cannot be parsed (for example unsafe YAML tags),
   - the markers are missing, duplicated, or reversed,
   - a different note id lives at the path (a human file),
   - the note is not tracked in `vault_notes` and its generated content differs
     (for example after a database restore),
   - the hash of the on-disk generated properties and region matches neither
     `vault_notes.last_generated_hash` nor `pending_generated_hash` (a human
     edited generated content). When the note's `generated_at` is later than
     the database's `last_written_at`, the reason says instead that the
     database is older than the note (for example a restored backup), because
     then seo-agent cannot tell whether the content was edited,
   - a new generated property would replace a different human property value, or
   - a shared list property (`tags`, `aliases`, `cssclasses`) on disk is a map
     rather than a list or a single value.
   Before declaring a conflict, a note whose generated part already equals the
   new content is adopted (`unchanged`) and re-recorded.
7. If the new generated content equals what is on disk, the result is
   `unchanged` and nothing is written.
8. Otherwise merge. The frontmatter is edited in place with the `yaml`
   Document API: generated keys are set (unchanged values keep their nodes)
   or removed (a comment above a removed key moves to the next key), and
   everything else (human keys, comments, key order, quoting) is untouched.
   For `tags`, `aliases`, and `cssclasses` the result is the union of
   seo-agent's entries and the entries on disk (a human-added tag is kept; a
   removed `seo-agent/...` tag is added back on the next update). The edit is
   verified by parsing it back; if it does not round-trip exactly, the block is
   re-serialized from values instead. The human text before and after the
   markers is copied verbatim, and the region is replaced.
9. Crash consistency: before replacing the file, the writer records the hash
   it is about to commit in `vault_notes.pending_generated_hash` (and the owned
   keys in `pending_generated_keys_json`); the database update after the write
   sets `last_generated_hash` and clears the pending columns. A crash or a
   database error between the rename and that update therefore leaves a
   pending hash that matches the file, and the next render (and `vault check`)
   accepts it instead of reporting a human edit. If the write itself fails, the
   pending hash is cleared (or a placeholder row for a new note removed) unless
   the new content is already on disk. The replacement is atomic (temp file,
   fsync, rename) and guarded by an optimistic check that the file did not
   change while seo-agent was working; if it did, the result is a conflict.

`vault_notes` stores `last_written_hash` (whole file), `last_generated_hash`,
`generated_keys_json` (which properties the generator owned), ownership, the
open `conflict_path`, and the pending hash and keys of a write in progress.
Hashes recorded by earlier versions (which covered `tags`) are still accepted
once, so an upgrade does not look like an edit.

### Conflicts

The artifact is written next to the note as
`<name>.conflict-<YYYYMMDDTHHMMSSZ>.md`. It contains the reason, resolution
steps, the generated region currently on disk, and the proposed generated
content (both as code blocks so they are never parsed as a live note). The same
proposal against the same file content does not create a second artifact. Each
conflict is also written to the audit log (`vault.conflict`) and the system log.

Resolution (`vault resolve <path>`):

- `--use-generated`: copies the current note into
  `14 System Logs/Conflicts/<folder - path - name>.backup-<timestamp>.md` (as a
  code block; the folder is part of the name, and `-2`, `-3`, ... is appended
  when that name is taken, so a backup is never skipped), re-baselines the
  stored hash, and lets the next `vault render` replace the region. If the
  backup cannot be written, the command fails before the database is changed.
  Text outside the markers is still preserved.
- `--detach`: marks the note human-owned; the writer no longer updates it.

### Other writer methods

- `link(toRelPath, alias?)` returns `[[folder/Note|alias]]` and throws
  `NOT_FOUND` unless the target exists or was registered with `plan()` in this
  run (`unplan()` withdraws a registration). The renderers link through the
  render plan instead, which applies the same rule (see Renderers).
- `readNote(relPath)` parses safely (no symlinks, strict YAML).
- `appendSystemLog(line)` appends `- <ISO timestamp> <line>` to
  `14 System Logs/<YYYY-MM-DD>.md`, where the date is taken in the business time
  zone (`reporting.businessTimezone`, falling back to the scheduler zone). Lines
  are redacted with `src/security/redact.ts`, made single-line, and the markers
  are neutralized. The file is opened with `O_APPEND` and fsynced; earlier
  entries are never rewritten.
- Dry-run writers (`ctx.dryRun` or `createVaultWriter(ctx, { dryRun: true })`)
  compute outcomes without touching files or the database.

## Links and file names

- Every generated link uses the full vault path ("Absolute path in vault"), for
  example `[[02 Website/Pages/Pricing|Pricing]]`. Shortest-path links are never
  generated. In tables the pipe is escaped (`\|`), as Obsidian requires.
- When a file name contains a dot (for example `04 Competitors/rival.example.test`),
  the link keeps the explicit `.md` so the name cannot be read as another file
  type: `[[04 Competitors/rival.example.test.md|rival.example.test]]`.
- File names are readable and stripped of `\ / : * ? " < > | # ^ [ ] %`,
  control characters, leading and trailing dots, and Windows reserved names.
- Stable ids: each note's `id` property is the record id (`page_...`,
  `kw_...`), or `<content_item_id>.brief` / `.draft`, `dashboard-<site>`,
  `vault-index-<site>`, `content-farm-<site>`, `ai-search-<site>`.
- Path stability: the planner reuses the path recorded for a note id, so a
  changed page title or keyword spelling never renames the file. A new note
  whose readable name is taken by another note (planned, tracked, or a human
  file) gets a deterministic suffix: `Name (a1b2c3).md`.

## Renderers (`renderAll(ctx, writer, opts)`)

`renderAll` plans every note first, then builds and writes entity notes, then
the index and the dashboard, so the dashboard reflects conflicts detected in
the same run. Options: `only` (subset of `dashboard, index, pages, keywords,
competitors, experiments, decisions, learnings, sources, content, ai_search`;
a kind that is not rendered is linked only if its note is tracked in its
folder AND the file is on disk), `limits`, `windowDays` (default 28),
`integrationStatuses` and `integrationStatusNote` (see Integration status). It
returns a summary with per-note outcomes, conflicts, errors, and `withdrawn`,
and returns `status: 'disabled'` when `features.obsidian` is false.

**Stale notes** (`src/obsidian/stale.ts`). When the record behind a generated
entity note no longer exists (for example keywords merged by migration 0203,
an owner decision withdrawn from `01 Business/Owner Decisions.md`, a deleted
learning), `vault render` marks the note stale in place instead of leaving it
looking current: frontmatter `status: stale` with `stale_reason` and
`last_generated_at`, a STALE banner at the top of the generated region, and
the last generated content for reference. The write goes through the
VaultWriter, so text outside the generated markers is kept and an edited
generated region produces a conflict artifact. Notes are never deleted or
moved; detached (human-owned) notes, other render kinds, and dry runs are
never changed; the content is deterministic, so re-rendering changes nothing.
A note whose record still exists but is beyond a render limit is not stale,
and a restored record un-stales its note.

**One writer for content notes; legacy duplicates.** The vault renderer is the
only writer of content notes: the `content` commands render them through
`renderAll(ctx, writer, { only: ['content'] })` after they change records, like
`vault render` and the content queue's `queue_notes` stage
(`src/cli/commands/content.ts`; `src/content/notes.ts` only builds readable
presentations used as data). Earlier versions of those commands wrote a second
set next to the renderer's notes (`<title> <id6>.md`, `<title> <id6> brief
v<n>.md`, `... draft v<n>.md`, `11 Content Farm/Content Pipeline.md`; types
`content_item`, `content_brief`, `content_draft`, `content_pipeline`; ids
`content-item-*`, `content-brief-*`, `content-draft-*`, `content-pipeline-*`),
which nothing updates any more. When content notes are rendered, each tracked
one is marked stale in place (`markSupersededContentNotes`): `status: stale`,
`stale_reason`, `superseded_by` (the current note's path), a banner linking to
the current note, and its old generated content (stage, status, approval
requests) removed so it cannot read as current. Text outside the markers is
kept, an edited region gets a conflict artifact, the note is never deleted, and
re-rendering changes nothing. The index lists it under "Stale notes" as a
duplicate of the current note. `vault check` reports every legacy note, tracked
or not, as `stale_duplicate` (warning) with the current note's path and the
next step (copy anything you added into the current note, then delete the
legacy file).

No generated link is left dangling by a failure in the same run: a planned
note that fails to build, or a new note that fails to write, and that does not
exist on disk, is withdrawn from the plan. Notes built afterwards show plain
text instead of a link, notes already written that linked to it are rebuilt and
rewritten, and the summary (and the system log) lists it under `withdrawn`.

### Integration status

`vault render` never makes network requests. The dashboard always shows the
vault's own status (`obsidian`: ready, degraded when the vault was not
initialized from the template, or disabled). Other integrations appear only
when the integration layer registers a provider with
`registerIntegrationStatusProvider(fn)` (`src/obsidian/status.ts`); it is
called with `{ network: false }`, for example with the doctor's offline checks.
Without a provider the dashboard says that the other integrations were not
checked and points to `doctor`; a failing provider is reported the same way.
Offline statuses show the check date only, so an unchanged status does not
rewrite the dashboard on every render.

### Untrusted text

Every string from the database is escaped before it is placed in a note
(`markdown.ts`). Generated markers are neutralized, and a single-pass escaper
backslash-escapes (or turns into an entity) everything that Markdown, Obsidian,
or a common plugin could make active:

- links of every form: `[`/`]` (wikilinks, embeds, Markdown links and images,
  reference links and definitions, callout markers, task checkboxes), `<`/`>`
  (raw HTML, angle-bracket autolinks), a colon before `//` (bare-URL autolinks
  for every scheme, including `obsidian://`), and the dot of `www.`;
- code and queries: backticks and `~~` runs (no code span, so no Dataview
  inline `= ...` / `$= ...` query, and no fence, so no `dataview`/`dataviewjs`
  block), the second colon of `::` (Dataview inline fields `[key:: value]` and
  `key:: value`), `$` (math), and `<`/`>` (Templater `<% %>`);
- tags (`#tag`) and Obsidian comments (`%%`);
- the backslash itself, first, so input cannot cancel an escape.

The text still reads the same when rendered. Single-line text uses `inline`;
multi-line text (evidence excerpts, forum signals, notes on record) is quoted
line by line with `quoteUntrusted`; ids, hashes, and URLs are shown literally
with `code` (a code span whose fence is longer than any backtick run inside;
text that starts with `=` or `$` or contains `<%` is shown as escaped text
instead, so it cannot be a Dataview inline query or a Templater tag). Model
drafts and multi-line brief fields go through `sanitizeDraftMarkdown`, which
keeps headings (demoted two levels), blockquotes, lists, and tables and escapes
everything else the same way. Scraped or model-written text therefore cannot
close the generated region, inject properties, create links or embeds, run a
query or script, or claim trust.

**Bidi controls are shown, not applied.** `inline`, `cell`, `code`, and
`quoteUntrusted` replace the bidi embedding, override, and
isolate controls (U+202A-U+202E, U+2066-U+2069) with visible `[U+XXXX]`
markers (`markBidiControls`, the same markers as the CLI's terminal-safe
output in src/core/terminal.ts), so an imported keyword or title with a
right-to-left override cannot make the H1 or the body read differently from
the stored text. Wikilink aliases use `(U+XXXX)` instead, because square
brackets would break the link. The marks U+200E (LRM), U+200F (RLM), and
U+061C (ALM) are kept: legitimate right-to-left text uses them and they cannot
reverse a run of text. New note file names drop these controls entirely
(`safeFileSegment` removes default-ignorable code points). Generated property
values (for example `title`, `keyword`, and every text entry of a list
property) are marked the same way by the writer (`buildGeneratedProperties`
marks before `sanitizePropertyText`, so a marker next to `[` or `]` cannot
form `[[` or `](`; the marking is not part of `redactVaultText`, which file
names and the path secret check also use). Model drafts and multi-line brief
fields (`sanitizeDraftMarkdown`) are marked too, so the draft a reviewer reads
before `content mark-reviewed` reads the same as the stored body, and so is
the JSON-LD of a draft's structured-data proposal. `codeBlock` keeps the
controls on purpose: the backup that
`vault resolve --use-generated` writes of a human-edited note is a code block
and keeps the human's text as written.

**Secrets never enter the vault.** Before a note is written, its body, title,
and every generated property value are redacted (registered secrets and
credential shapes such as Google access tokens and API keys), and credential
parameters in URLs (`token=`, `sig=`, `X-Amz-Signature=`,
`X-Amz-Credential=`, `X-Amz-Security-Token=`, a fragment `access_token`) are
masked while other query parameters stay. Note file names and wikilink
aliases are planned through `noteFileName`, which redacts secrets too.
Untrusted names never become hidden or unsafe file names: leading dots and
whitespace are stripped repeatedly after separators collapse, so titles such
as `. . . x`, `../../x`, or `.obsidian/plugins/evil` become visible names
under their folder, and a hostile name can no longer abort `vault render`.

**Wikilink aliases are untrusted text too.** The display text of
`[[target|alias]]` comes from titles, Search Console queries, domains, and
scraped source titles. A plain CommonMark/GFM viewer does not parse `[[...]]`,
so it would render an alias as ordinary inline Markdown. `sanitizeLinkAlias`
(src/obsidian/wikilinks.ts) therefore redacts secrets, replaces the
link-breaking characters `[` `]` `|` and line breaks with spaces, and applies
`escapeLinkAliasText` (src/obsidian/markdown.ts), the alias counterpart of
`inline`: `<` `>` become `&lt;` `&gt;` (no raw HTML or Templater `<% %>`), `&`
that does not start an entity becomes `&amp;`, `$` and `\` become `&#36;` and
`&#92;` (no math, and no backslash that could escape the closing `]]`),
backticks become `'` (no code span, so no Dataview `= ...`/`$= ...` inline
query), `::` becomes `: :` (no Dataview inline field), and `%%` becomes `% %`.
Aliases avoid backslash escapes because a backslash inside a link can break it.
Whether Obsidian decodes entities inside an alias was not verified: it may show
`&amp;` literally, which trades display fidelity for safety in plain viewers.
New note file names also turn backticks into `'`, so a link target never holds
a code span. A note keeps the path recorded in `vault_notes`, so an existing
note whose name contains a backtick keeps its name and is not renamed.

## Business-note sync (`business-sync.ts`)

Supported note types (the `type` property is required):

| Type | Default note | Format |
| --- | --- | --- |
| `business_profile` | `01 Business/Business Profile.md` | `## Offer`, `## Target customer` (text); `## Differentiators`, `## Approved claims`, `## Prohibited claims`, `## Editorial requirements` (bullets); `## Product facts` (`- [fact-id] Statement. (source: ..., verified: YYYY-MM-DD)`); `## Brand voice` (text) |
| `customer_questions` | `01 Business/Customer Questions.md` | `## Questions` bullets |
| `owner_decisions` | `01 Business/Owner Decisions.md` | `## Decisions` bullets `- YYYY-MM-DD: decision` (knowledge only; never authorizes actions). With `--apply`, the entries are synced into `decisions` (`decided_by` owner, `vault_path` the note), idempotent per note revision; a removed entry is withdrawn and audited. A decision can only exclude a candidate from recommendations (for example `- 2026-09-01: reject https://example.com/page: reason`); subjects resolve to a page id, normalized URL, or opportunity id, off-site URLs are ignored, and anything else is site-wide. An imported decision applies whatever its age until its bullet is deleted (recommend reads `decisions` rows with a `vault_path` without the 180-day window); only decisions recorded from approvals and rejections use the 180-day window. The template's comment says so; a vault created from an earlier template keeps its old comment (`vault init` never overwrites), which said that every decision counted for 180 days. |
| `business_note` | any | Free-form sections |

Rules:

- Validation uses zod schemas plus cross-checks (duplicate fact ids, a claim
  that is both approved and prohibited, dates, lengths, one profile per site,
  unique ids, `site` must match). HTML and `%%` comments are ignored. An empty
  section means "no change"; `(none)` clears a list or marks the offer or
  target customer unknown.
- Properties such as `approved`, `trusted`, `trust_class`, `verified`,
  `authorized_*` are ignored and reported. They never approve or trust anything.
- A note is rejected when it contains the generated markers, is tracked as a
  generated note, uses a generated note type, or reuses a generated note id.
  Agent-generated or scraped text therefore cannot become an owner fact by being
  copied into `01 Business/`. Symlinks are never followed.
- `vault import-business` validates and shows the config diff without writing.
  `--apply` records a version in `business_note_versions` (`version` increments
  per note; identical content is not recorded twice). Invalid notes are recorded
  as `rejected` with their errors. Recording never changes the site config.
- `vault apply-business` recomputes the diff for the current, recorded profile
  and prints a diff hash that covers the site, note path, note content hash,
  base config hash, and changes. Only `--confirm <hash>` writes: the YAML config
  is edited in place (comments elsewhere survive), round-trip validated, backed
  up to `<workspace>/backups/config/`, replaced atomically, and a config version
  is recorded with source `business_note_sync` (`ensureSite`; when the new
  config is identical to an earlier recorded version, `ensureSite` makes that
  version active again instead of adding one, and the result says so). Every
  application is appended to `business_profile_applications` (config version,
  diff hash, changes, who, when); the version row's `applied_config_version`,
  `applied_at`, and `applied_by` hold the latest one. An audit event
  `config.business_note_sync` is written. A changed note or config changes the
  hash, so a stale confirmation is refused (`APPROVAL_INVALID`). The actor is
  a named human: `--by <name>` is validated like an approver name
  (automation and account names such as `system`, `claude`, `scheduler`,
  `agent`, `owner`, or `root` are refused, in the preview as well), and
  without `--by` the operating-system user is recorded unless it is a
  service account such as `node` (the container) or `runner` (CI), which is
  refused with a hint to pass `--by`; there is no anonymous `owner` default
  (`tests/integration/approvals/human-actor-names.test.ts`).
- Revisions: `business_note_versions` has one row per distinct content of a
  note. Every recording is also a row in `business_note_revisions`, so a note
  that returns to earlier content (A -> B -> A) is recorded as a new revision
  of the existing version (reported as "returns to the content of v1"), never
  as "already recorded". `apply-business` refuses to apply content whose
  latest change has not been recorded.
- Each `import-business --apply` re-derives the status of the recorded
  business profile against the current site config: `pending_review` when the
  config differs from the note, `imported` when it matches (audit event
  `vault.business_note_status_changed`). A reverted profile is therefore not
  trusted while the config still holds the other content.
- `businessNoteTrustClass(row)`: `rejected` has no trust; `pending_review`
  (recorded, but the config differs) is `user_reported`; `imported` (applied, or
  matching the config, or a non-profile note) is `owner_approved`. Trust always comes
  from these code-checked states, never from note properties.

## CLI

```
npm run cli -- vault init                     # create the site vault from the template (never overwrites)
npm run cli -- vault render [--only pages,keywords] [--dry-run] [--json]
npm run cli -- vault check [--json]           # exit code 1 on errors (broken links, malformed notes); stale duplicates are warnings
npm run cli -- vault import-business [--apply]
npm run cli -- vault apply-business [--confirm <diff-hash>] [--by <name>]
npm run cli -- vault business-history [--note "01 Business/Business Profile.md"]
npm run cli -- vault resolve "<note path>" --use-generated | --detach
```

`vault render` exits with code 3 when `features.obsidian` is disabled, and 1 when
a note failed to render (withdrawn notes are listed). Conflicts are reported but
are not errors. `vault render` collects the offline integration statuses for the
dashboard (see Integration status). `vault business-history` lists each version
with the revisions at which the note had that content, whether it is current,
and every application to the config.

## Template (`vault/_template/`)

The full folder tree from the spec (00 Dashboard to 14 System Logs, plus
Templates), a README explaining ownership, the three `01 Business` notes, and
`Templates/` notes for pages, keywords, competitors, experiment ideas,
decisions, learnings, and briefs (Obsidian core Templates placeholders only).
`Dataview Examples (optional).md` shows optional queries; the vault does not
depend on Dataview. `vault init` fills `{{site_id}}` and `{{business_name}}` in
notes outside `Templates/`, never writes into `.obsidian/`, and never
overwrites.

## Verified contract usage

Obsidian conventions follow `docs/integration-contracts.md` section 8 (sources
QN31 to QN38, retrieved 2026-09-24): Markdown files written directly (Obsidian
picks up external changes), never writing `.obsidian/`, YAML properties between
`---` lines with `tags`/`aliases`/`cssclasses` as lists, tags without `#` using
`/` for nesting, quoted links inside properties, flat properties only, links
with paths from the vault root, `\|` inside tables, and Dataview treated as an
optional community plugin.

Not verified against a running Obsidian app (no Obsidian instance was used in
development):

- Resolving `[[folder/name.with.dots.md|alias]]` links. Obsidian documents
  paths and aliases in links; including the `.md` extension is a defensive
  choice for dotted names. Open the vault and click such a link to confirm.
- The escaping of untrusted text follows CommonMark/GFM rules (a backslash
  escape or an entity never forms syntax; a backslash inside `scheme://` or
  `www.` stops the autolink extension), Dataview's documented inline-field and
  inline-query syntax, and Templater's `<% %>` tags. It was not checked in
  Obsidian's reading view and live preview; open a source note with scraped
  text and confirm that no link or query is rendered.
- Whether Obsidian's Properties view renders a `scheme: //...` text value as a
  link (seo-agent writes non-http(s) URIs in generated properties that way).
- How Obsidian's Properties editor re-serializes frontmatter after a human
  edits a property. Values are compared semantically (and empty values are
  treated as equal), so formatting changes should not cause conflicts, but a
  type change made in the Properties editor (for example a number to text) on
  a generated property will be treated as an edit and produce a conflict.

## Data sent externally

None. The vault layer only reads SQLite and writes local files. It makes no
network requests and needs no credentials. If you place the vault in a folder
synced by a third-party service (Obsidian Sync, iCloud, Dropbox, Git hosting),
that service receives your notes. That includes business facts, page metrics,
and research excerpts, so choose sync deliberately. Secrets never enter the
vault: log lines pass through redaction and no renderer reads the secret store.

## Limitations

- Brief and draft notes show the latest version per content item (with version
  history); earlier versions are not rendered as separate notes.
- `vault_path` columns owned by other modules (`decisions`, `content_briefs`,
  `content_drafts`, `reports`) are not updated by the renderer.
- Weekly and monthly reports (`07 Reports/`) are written by the reports module;
  this module only lists recent `reports` rows on the dashboard.
- The dashboard shows other integrations' status only when a status provider
  is registered (the integration layer should register the doctor's offline
  checks); otherwise it shows the vault's own status and says the others were
  not checked. `renderAll` called directly without statuses falls back to the
  configured feature flags, labeled as not a connectivity check.
- The frontmatter of a generated note is edited in place, which keeps comments,
  key order, and quoting; the `yaml` library still normalizes some whitespace
  of the lines it re-emits (for example flow lists are written as `[a, b]`,
  and indentation becomes two spaces). If an in-place edit cannot be verified,
  the block is re-serialized from values (comments inside it are lost, with a
  logged warning).
- A `seo-agent/...` tag that the generator no longer produces (the note's kind
  changed) stays as if a human had added it.
- The escaping covers Dataview's default inline-query prefixes (`=` and `$=`).
  If you configure other prefixes, a code span that starts with them is not
  recognized; seo-agent shows untrusted text in code spans only for ids,
  hashes, URLs, and paths. Bare e-mail addresses in untrusted text may still be
  autolinked as `mailto:` links by some renderers (the address is shown as is).
- A crash between the file write and the database update is recovered
  precisely (pending hash). A database restored from an older backup is not:
  notes rendered after that backup can no longer be verified and produce a
  conflict whose reason says so; resolve them with `vault resolve
  --use-generated` after checking them.
- `ensureSite` (foundation) reuses an existing config version when the config
  is identical to it, so re-applying an earlier profile activates the earlier
  config version rather than adding a new one; `business_profile_applications`
  records the application either way.
- Filesystems without hard links fall back to an existence check plus rename
  for create-only writes, which has a small race window.

## Next steps for access

No credentials are required. To browse the vault in Obsidian (optional):
install Obsidian, choose "Open folder as vault", and select
`<workspace>/vault/<site-id>`. Keep Obsidian's default settings or set "New
link format" to "Absolute path in vault" so links you create match the
generated ones. Keep Dataview's JavaScript queries and Templater's "trigger on
new file creation" off unless you need them (see Untrusted text).

For the integration phase: register the doctor's offline checks with
`registerIntegrationStatusProvider((ctx, { network }) => statuses)` from
`src/obsidian/status.ts` (or `src/obsidian/index.ts`) so the dashboard shows
every integration; `vault render` always calls it with `network: false`. The
vault writer is available as `createVaultWriter(ctx)` from
`src/obsidian/writer.js`, `src/obsidian/vault.js`, or `src/obsidian/index.js`.
